P0并发与 JVM 调优实战

为什么重要：外包项目最常见的「线上救火」是线程池打满、Full GC、锁竞争导致接口超时。能在 30 分钟内定位到「线程/锁/GC/下游」哪一层，是可迁移的硬通货。

JMM、可见性与 Happens-Before

JMM 回答的不是「多核怎么跑」，而是「什么时候写对其他线程可见」。资深面试官要的是你能把 volatile、synchronized、final、锁释放/获取映射到 HB 边，而不是背定义。

  • 可见性：写缓冲 / 缓存行导致其他核看不到最新值；volatile 写插 store-store/store-load 屏障语义（按平台实现）。
  • 有序性：编译器与 CPU 重排；单线程 as-if-serial，多线程需同步边。
  • 原子性：long/double 非原子写在 32 位历史问题；业务上用 Atomic* / 锁。
  • 常见坑：双重检查锁定必须 volatile 实例；把 volatile 当锁用做复合操作（check-then-act）必挂。
flowchart LR
  W[线程A 写共享变量] --> B1[释放锁 / volatile写 / 解锁]
  B1 --> HB[Happens-Before]
  HB --> B2[加锁 / volatile读]
  B2 --> R[线程B 读到一致视图]

资深原则
先画「谁写、谁读、有没有同步边」；没有边就别谈「偶现」——偶现通常是缺失 HB。

锁：synchronized / ReentrantLock / 偏向与自旋

生产里真正伤的是锁粒度与锁顺序，不是「用哪种锁」。偏向锁/轻量锁是 JVM 优化故事，面试可提，但落地优先：缩短临界区、避免在锁内 IO、固定加锁顺序防死锁。

手段适用外包常见误用
synchronized短临界区、语义简单锁整个 Service 方法，RPC 打满
ReentrantLock需要超时/中断/公平/多条件忘记 unlock（必须 finally）
StampedLock读多写少且能接受乐观读校验当可重入锁用、写饿死未评估
分段 / 条纹锁热点 key 冲突分段过多导致上下文切换

线程池：参数、拒绝、隔离

线程池是「资源控制器」不是「越快越好」。核心公式思路：CPU 密集 ≈ 核数+；IO 密集看等待比。更关键的是队列类型与拒绝策略是否匹配业务（下单不能默默 Discard）。

// 面试可讲的「可落地」模板（示意）
ThreadPoolExecutor pool = new ThreadPoolExecutor(
  core, max, 60, TimeUnit.SECONDS,
  new LinkedBlockingQueue<>(capacity), // 有界！
  new NamedThreadFactory("pay-callback"),
  new ThreadPoolExecutor.CallerRunsPolicy() // 或自定义：打点+降级+告警
);
  • 隔离：核心链路 / 回调 / 导出报表分池，避免慢任务拖垮支付回调。
  • 可观测：活跃线程、队列长度、拒绝次数、任务耗时分位数必须进指标。
  • 陷阱：Executors.newFixedThreadPool 无界队列 → OOM；CachedThreadPool 突发打爆。

GC 与排查路径

先定症状：延迟尖刺（Young GC 停顿）、吞吐塌陷（Full GC）、内存缓慢爬升（泄漏）。JDK17+/21 常见 G1；大堆低延迟可评估 ZGC（看版本与运维熟悉度）。

案例：大促回调线程池打满

现象：支付回调 5xx，业务侧重复通知；容器 CPU 不高但 RT 飙升。根因：共用线程池被「对账导出」占满，回调队列堆积，超时重试雪崩。止血：回调独立池 + 有界队列 + 拒绝时快速失败并依赖支付平台重试幂等；导出限流到夜间。复盘指标：拒绝次数、回调成功率、对账延迟。

面试亮点说法
「我不只会调 core/max，我会按关键链路做线程池隔离，用有界队列和可观测拒绝策略把过载显性化；GC 问题先用分配速率和区域填充判断，再决定是代码分配路径还是堆/GC 器选型。」

落地实践清单

  • 所有业务线程池命名 + 有界队列 + 指标（活跃/队列/拒绝）
  • 核心接口压测时同时看 GC 停顿与线程栈采样
  • 准备一页「线上线程/GC 排查 runbook」可带走
  • 禁止无界缓存（本地 Map）无 TTL/无上限

P0Spring Boot / Spring Cloud 核心与生产问题

为什么重要：外包 80% 系统是 Boot 单体或「轻度 Cloud」。真正拉开差距的是：自动配置原理、事务失效、循环依赖、配置刷新、Feign/Gateway 超时与重试风暴。

核心原理（资深深度）

  • 自动配置：@EnableAutoConfiguration → AutoConfiguration.imports / factories；条件注解（@ConditionalOnClass 等）决定装什么。
  • Bean 生命周期：实例化 → 属性填充 → Aware → BeanPostProcessor 前后 → init → 销毁。AOP 代理时机决定「同类自调用事务失效」。
  • 事务失效清单：非 public、同类自调用、异常被吞、检查异常未 rollbackFor、传播行为误用、多数据源没绑定正确管理器。
  • Boot 3 / Jakarta：包名迁移、HttpClient 栈变化；接手项目先确认 Spring 世代，避免抄 Boot2 配置。

案例：遗留 Boot2 升级与循环依赖

接手「能跑但不能动」的单体：启动报循环依赖。资深做法不是盲目 allow-circular-references=true，而是：画出依赖环 → 提取接口/事件 → 构造器注入替代字段注入 → 把「初始化逻辑」移出构造。外包价值：用最小 diff 拆环，避免大爆炸重构。

P0数据一致性：事务、分布式事务、最终一致、Outbox、幂等

为什么重要：支付对账、库存、积分、优惠——外包最容易「看似成功实则不一致」。能讲清「强一致代价」并落地 Outbox/幂等，是架构判断力的证明。

原则分层

  1. 单机本地事务：能用本地事务解决的，不要上分布式事务。
  2. 尽量避免 2PC/XA：长事务锁资源、协调者故障难缠；外包运维通常扛不住。
  3. 业务可接受最终一致：用 Outbox / 事务消息 / 对账补偿，把一致性做成「可观测的过程」。
  4. 幂等是底线：网络会重试；至少做到「同一业务单号多次执行结果等价」。

幂等设计要点

  • 幂等键：业务单号 / 请求 ID；落库唯一索引，不要只靠「先查后插」。
  • 状态机：INIT→SUCCESS/FAIL；非法迁移拒绝并打点。
  • 至少一次投递：消费端必须幂等；精确一次几乎靠「去重表 + 事务」近似。

案例：支付对账

场景：渠道成功、本地失败或相反。做法：支付回调幂等更新；定时拉账单对账；差异单进挂账表人工/自动补单；金额字段用分（整数）避免浮点。亮点：把「对账差异率」做成 SLO，而不是靠感觉。

案例：库存超卖

方案梯度：DB 条件更新 stock = stock - 1 WHERE stock > 0 → Redis Lua/原子扣减 + 异步落库 → 分段库存。大促用预扣+超时释放。强调：缓存库存与 DB 必须以「权威源」定义清楚。

面试亮点说法
「分布式事务我默认用 Outbox/可靠消息做最终一致，并用对账闭环；强一致只留给资金底账。幂等用唯一约束和状态机，而不是靠『应该不会重复』。」
  • 列出系统内所有「跨资源写」并标注一致性策略
  • 核心写接口补齐幂等键与唯一索引
  • 至少做一版对账/补偿任务（可简陋但要有）
  • 明确消息投递语义与消费幂等证明
Q：Seata AT 模式原理与坑？
强答：AT 用 undo log 自动补偿，业务侵入小；坑是脏写隔离、长事务锁、与某些 ORM/批量更新不兼容、运维复杂度。外包若无平台支撑，优先业务级最终一致。

P0MySQL：索引 / 执行计划 / 慢查询 / 分库分表边界

为什么重要：外包性能问题一半在 SQL。会看 EXPLAIN、会判断「该不该分库分表」，比会背 B+ 树更值钱。

索引与执行计划（深度）

  • 最左前缀：联合索引 (a,b,c) 有效范围；范围条件后列难用到。
  • 覆盖索引：减少回表；选择性与写入代价权衡。
  • EXPLAIN 关键字段：type（ref/range/index/ALL）、key、rows、filtered、Extra: Using filesort/temporary。
  • 历史坑：隐式类型转换导致索引失效；OR 优化差；深分页 LIMIT 100000,10 用延迟关联/seek。
-- 深分页优化思路（示意）
SELECT t.* FROM orders t
JOIN (SELECT id FROM orders WHERE user_id=? ORDER BY id DESC LIMIT 20 OFFSET 1000) x
ON t.id = x.id;

事务与锁

InnoDB 行锁 + 间隙/临键锁（RR）防幻读；死锁看 SHOW ENGINE INNODB STATUS。外包常见：大事务（导入）拖垮在线；未加索引更新导致锁升级感（大量行锁）。

分库分表：何时不该拆

判断边界
单表 < 千万且无热点、查询维度单一、团队无人值守分片中间件 → 先优化索引/归档/读写分离。分片后的二次查询、跨库事务、扩容迁移成本常被低估。

案例：订单列表慢查询

商家后台「按状态+时间」筛选全表扫。落地：联合索引 (merchant_id, status, created_at)；强制分页上限；导出走异步任务与只读实例。

P0Redis：缓存模式、击穿/穿透/雪崩、分布式锁

为什么重要：缓存是性能加速器，也是一致性负债。分布式锁用错会「看起来安全其实裸奔」——面试高频，生产高危。

缓存模式

模式要点适用
Cache-Aside读：miss 装载；写：更 DB 删/更缓存最常见
Read-Through / Write-Through缓存组件代理有统一缓存层时
Write-Behind异步落库，丢数据风险允许丢失的计数类
延迟双删经验补丁，非银弹短窗不一致可接受

击穿 / 穿透 / 雪崩

  • 穿透（查不存在）：布隆过滤 / 空值短 TTL / 参数校验。
  • 击穿（热点 key 过期）：互斥重建 / 逻辑过期 / 永不过期+异步刷新。
  • 雪崩（大批同时过期或 Redis 挂）：TTL 抖动、多级缓存、限流降级、Redis 高可用。

分布式锁正确用法

红线
SET key value NX EX；value 用唯一令牌；释放用 Lua 校验令牌。红锁在多数外包场景过重且仍非银弹；锁粒度、续期（看门狗）、业务幂等比「算法名」重要。
  • 锁的是「资源」，不要锁整个方法名。
  • 持锁业务必须可重入/可恢复；超时要小于业务最坏耗时或可续期。

P1Kafka / RocketMQ：可靠投递与顺序

为什么重要：异步解耦是外包系统常见「救命稻草」，但消息丢、重复、乱序会直接变成资损。你要能讲清投递语义与顺序键设计。
